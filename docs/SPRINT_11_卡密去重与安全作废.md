## 去重导入

管理端不再写死productId=1，改为选择本店自动卡密商品及实际SKU。下架商品仍可管理库存，非卡密商品不进入选择列表，服务端再次校验商品/SKU/商户关系。旧导入路径和成功字段保持兼容：

```text
POST /api/v1/merchant/cards/import
{ productId, skuId, cardContents: [...] }
返回 importedCount、newStock
```

新发布的自动卡密商品初始库存必须为0，管理端禁用手填，后端拒绝非零数量；后续导入生成可售数量。实物/定制服务仍允许合法非负初始库存。旧商品的历史数量不会自动改写，存量漂移仍需另行核对。

每批1至1000条，每条最多4096字符；后端拒绝null、超长及规范化后为空的卡密，包括清理后为空的ASCII控制字符。去首尾空白沿用Java trim规则，大小写及内部字符保留；同批规范化后重复返回业务400。本店所有历史状态、所有SKU已有相同规范化内容时，整批返回409，不插入任何新卡，也不加库存。不同商户的历史不互相泄露或阻止导入。

比较时只在内存计算SHA-256摘要，错误文本不回显卡密。所有导入统一先锁商户，再锁商品和SKU，在READ_COMMITTED事务下读取本店全部历史内容，防止两个应用实例或不同SKU同时导入同一卡密。新卡插入和库存增量同事务，失败整体回滚；库存容量计入HELD未来释放数量，避免INT溢出。

这不是数据库唯一指纹约束。绕过应用锁直接写库的外部程序不受此去重保证；历史扫描尚未分页/索引化，后续规模化需要受控指纹迁移。不会自动删除、归并或作废已有重复卡密；历史记录必须保留，不能随意物理删除后再导入。

productId和skuId拒绝小数截断，仍兼容旧前端的十进制整数字符串。导入不要求新幂等头；网络结果不明时重试同批会被历史去重拒绝，用户应先核对列表，不能把409误认为第一批未入库。

## 安全作废

| 接口 | 权限 | 用途 |
| --- | --- | --- |
| POST /api/v1/merchant/cards/{id}/void | 绑定本店的店长或超管 | 请求reason，作废未售卡并扣减一份可售库存 |
| GET /api/v1/merchant/cards/{id}/void-record | 本店后台账号 | 查询原作废人、原因、前后数与时间，不返回卡密内容 |

卡密列表区分0未售、1已售、2已作废。作废原因必填、最多255字符，请勿填写卡密或个人信息。只有未售且未绑定订单的本店卡可作废；售出、未知状态或其他商户卡拒绝。SKU存在HELD预占时保守拒绝全部作废，待支付或释放后再操作；可售数必须大于0且与该SKU未售卡数量一致，不通过作废修补漂移。

锁顺序为商户、商品、SKU、目标卡，不锁预占行。状态CAS、SKU扣一份及追加virtual_card_void记录同事务提交；记录失败回滚卡状态和库存。卡ID是记录主键；同卡、同规范化原因重试只返回原记录，不再扣数，原操作人保持不变；更换原因重试返回409，不能覆盖原理由。历史作废但没有记录的卡也拒绝伪造新记录。

作废卡仍保留在历史表中，因此不能重新导入。作废不是删除、退款或补发，不能撤回已交付卡密。本轮不增加作废恢复入口。记录仅追加，数据库管理员仍可能修改，不宣称不可篡改。

### 已编写的验收用例

| 场景 | 用例覆盖 |
| --- | --- |
| 初始库存 | 自动卡密0合法，null/负数/非零拒绝；实物/服务合法数量保留；新发布→导入→作废后的数量与在库卡数一致 |
| 导入边界 | 空批、空白、null、控制字符清理为空、1001条、4097字符、批内去重、大小写保持、整数ID及旧数字字符串兼容、小数/溢出拒绝 |
| 历史与隔离 | 已售/未售/作废均参与本店去重；跨商品并发导入仅一次成功；不同商户不串数据 |
| 作废边界 | 售出、绑定订单、未知状态、预占、零库存、数量漂移、非本店、员工写入拒绝；无效操作人/ID、空白/超长原因、历史作废缺记录拒绝 |
| 重试与争用 | 同卡同原因只扣一次；改原因不覆盖记录；并发作废只扣一次；发卡与作废争用最后一张卡只能一方成功 |
| 事务与SQL | 导入加库存失败回滚插入；作废扣库存失败回滚卡状态；写作废记录失败回滚状态与数量；拒绝外层错误隔离；MySQL建表/记录保留/Mapper与回滚 |
