# 提交说明模板使用说明

## 1. 模板位置

模板文件：[.gitmessage](../.gitmessage)

模板以 `#` 开头的行是写给填写者的说明，git 在生成提交说明时会忽略这些行。实际提交时保留字段名并填写内容即可。

## 2. 如何启用

在仓库根目录由用户手动执行以下命令，只对当前仓库生效：

```bash
git config commit.template .gitmessage
```

如需确认是否启用：

```bash
git config --get commit.template
```

说明：

- 不推荐使用 `git config --global commit.template`，避免影响其他仓库。
- 代理不会自动执行上述命令，也不会修改 `.git/config` 或全局 Git 配置。
- 未启用模板时，提交仍可正常进行，但不会自动带出字段结构。

## 3. 字段怎么填

### 3.1 标题行

格式：`<类型>(<范围>): <简述>`

- 类型：`feat`、`fix`、`docs`、`test`、`refactor`、`chore`、`deploy` 等。
- 范围：受影响模块或文档域，例如 `merchant`、`order`、`payment`、`auth`、`docs`、`deploy`。
- 简述：一句话说明本次提交“为什么做”，不要只写“update”或“修改”。

### 3.2 问题范围

填写对应的主台账 D/F 编号、复查 R 编号或修复清单 T 编号，并写明本轮实际子范围。

- 不要写“全部修复”。
- 部分完成时保留“部分修复/部分实现”，不要把整个业务域标为完成。
- 原清单外的独立功能应单列候选，不混入既有修复任务。

### 3.3 具体行为变化

只写实际发生的代码、接口、数据、配置或文档变化。

- 没有运行行为变化时写“无行为变化，仅文档/注释”。
- 行为变化与注释、文档变更不要混写，避免借补注释夹带行为变化。
- 涉及事务、锁、权限、敏感字段、状态机、接口兼容、迁移前提时要点明。

### 3.4 验证状态

必须区分以下两类，不能含糊：

- **未运行**：未执行编译、测试、构建、部署，未连接数据库。适用于只读审查、纯文档交付等。
- **用户手动执行通过**：写明准确命令、执行时间与结果范围，例如：

  ```text
  用户手动执行通过：mvn -f shop-b2b2c-backend/pom.xml test；执行时间：2026-11-06 15:30；结果：通过（H2 隔离测试，未连接真实 MySQL）。
  ```

注意：

- 代理只能写到“已实现·待人工验证”，不能自行填“已验证”。
- H2 通过不能替代真实 MySQL 或渠道联调；跳过项要注明“跳过不算通过”。
- 测试环境、命令和范围要写清，避免把一次局部通过写成全量验收。

### 3.5 未完成或风险

写残留子项、未验证项、环境依赖、兼容或迁移风险。

- 没有就写“无”。
- 有未完成事项时，不要用“后续再看”代替具体范围。
- 涉及存量迁移、回滚、生产凭据轮换的，要写明由谁执行、尚未执行。

### 3.6 执行方

固定字段，只能使用以下取值：

- `执行方: Trae`
- `执行方: ChatGPT`
- `执行方: 人工`

未填写的提交视为“未标注执行方”。不要用“代码代理”“开发”“团队”等模糊写法代替固定字段。

## 4. 为什么需要标注执行方

- 多人/多代理协作时，提交说明是区分“谁实现、谁验证”的第一手记录。
- 代理执行与人工执行的责任边界不同：代理负责实现、用例、静态审阅和文档；编译、测试执行和生产构建按约定由用户手动运行。
- 未标注执行方的提交，后续无法判断验证结论来自代理静态阅读还是用户实际执行，容易把“待验证”误当“已验证”。
- 标注执行方不替代验收；验收状态仍只由用户反馈决定。
