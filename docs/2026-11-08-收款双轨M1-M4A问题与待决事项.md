## 2. 阻塞问题（需要决策）

### 问题 1：平台代收目前“可配置、可切模式，但无法支付”

事实：

- `PaymentGatewayService` 仍按阶段一规则拒绝 `PLATFORM_COLLECT` 订单发起支付。
- 平台代收需要平台自己的服务商商户号、证书、APIv3 密钥与回调配置；当前仓库只有商家级渠道配置，没有平台级配置项。
- `PlatformCollectionService`（T40 骨架）默认 `platform-collect-enabled=false`，且支付回调履约未调用其台账/分账方法。

可选方案：

| 方案 | 内容 | 代价/风险 |
| --- | --- | --- |
| A（默认建议） | 先补“平台收银台配置键 + 适配器接口 + mock 实现 + 下单支付拒绝原因细化”，不接真实资金；等凭据后只换适配器实现 | 需要新增配置契约，mock 不得被当成联调通过 |
| B | 暂缓平台代收支付，先做 M5 的直收对账、分账异常队列与灰度 | 平台代收仍是半成品，商家切过去会停售 |
| C | 等真实服务商凭据到位再继续 M4-B/M6 | 夜间无更多代码产出，但风险最低 |

### 问题 2：商家可被切到平台代收，但资质开关未开时该商家新订单会全部 409

**状态：已按方案 A 解决（2026-11-09，Sprint 55，代理实现待人工验证）**：`switchMode` 切平台代收前置增加资质硬闸校验，未启用 409“分账通道未启用”，先于绑定三要素；详见 [Sprint 55](SPRINT_55_切平台代收前置增加资质校验.md)。

事实：

- M1 切换前置只校验 `binding_status=BOUND`、`sub_mchid`、`settlement_account_id`（已确认规则）。
- M4-A 下单时额外要求资质开关 `PLATFORM_COLLECT_ENABLED=true`，否则 409。
- 因此运营若在资质未开通时切换商家，该商家所有新订单会被阻断。

可选方案：

| 方案 | 内容 | 代价/风险 |
| --- | --- | --- |
| A（默认建议） | 把“资质开关已启用”加入切换前置校验，未启用时禁止切平台代收，并返回明确原因 | 改变 M1 已确认的切换校验范围，需要你确认 |
| B | 保持现状，仅在管理端切换弹窗增加警示文案 | 运营仍可能误操作导致商家停售 |
| C | 切换允许，但下单时自动按商家直收处理 | 与“不得静默降级”冲突，不建议 |

### 问题 3：`merchant_payment_account` 没有写入流程

**状态：已按方案 A 解决（2026-11-09，Sprint 56，代理实现待人工验证）**：结算账户核验通过且成为默认账户时同步 upsert `merchant_payment_account`（channel 取店铺 pay_channel、settlement_account_id 引用已核验账户），状态按真实值（AUDITING/UNBOUND/sub_mchid 空串），不伪造 PASSED/BOUND；渠道字段仍只允许真实渠道结果推进。详见 [Sprint 56](SPRINT_56_结算账户核验通过同步渠道台账.md)。

事实：

- 全仓库未发现向 `merchant_payment_account` 写入业务数据的代码，只有 Mapper 的保存方法与读取。
- T39 入驻流程写的是 `merchant_settlement_account`；两者不是同一张表。
- 因此除测试夹具外，切平台代收大概率因“无 BOUND 账户”被 409。

可选方案：

| 方案 | 内容 | 代价/风险 |
| --- | --- | --- |
| A（默认建议） | 入驻/结算账户核验通过时，同步写一条 `merchant_payment_account`（渠道取店铺 `pay_channel`，结算账户 ID 引用已核验账户），状态按真实值，不伪造 PASSED | 两张账户表出现冗余，需要明确以哪张为权威 |
| B | 新建“渠道进件”独立接口与页面，专门维护 `merchant_payment_account` | 工作量更大，但职责清晰，适合 M6 前完成 |
| C | 继续只读，平台代收暂不对外开放 | 与 M3 管理端入口的预期不符 |

### 问题 4：两个“总闸”语义重叠，需要在文档与页面统一口径

事实：

- 数据库 `platform_collection_config.enabled`：运营可开关的灰度总闸（M1）。
- 环境变量 `PLATFORM_COLLECT_ENABLED`：进程级资质/联调硬闸（T40）。
- 当前实现：两者都为真且商家配置为平台代收时，订单才会快照 `PLATFORM_COLLECT`。

默认建议：明确写成“环境变量=资质硬闸（只有完成真实联调才能打开）；数据库总闸=运营灰度开关（可按期关闭）”，管理端只展示数据库总闸，环境硬闸仅以只读标识呈现。若你同意，M5/M6 文档按此口径固化。

## 3. 中等风险与技术债（不阻塞今晚交付）

1. **平台代收退款仍被拒绝**：`RefundTransactionService` 沿用阶段一守卫，`PLATFORM_COLLECT` 订单退款会在入口 409；需与 M4-B 一起接“先退分后退款”。
2. **支付回调不识别平台代收**：回调校验按商家子商户号匹配，平台代收订单目前无法进入履约；M6 需按平台商户号校验并生成台账。
3. **总闸变更无独立历史表**：只有当前值与最后更新人，无法追溯开关历史；M5 可评估增加只追加表。
4. **M3 未做浏览器视觉验收**：弹窗、总闸卡片、长文案与窄屏布局均未截图确认。
5. **H2 与 MySQL 默认值差异**：部分测试夹具显式写了状态值才避免默认值分歧；真实 MySQL 行为仍需人工验证。
6. **历史订单不回填**：旧订单保持原 `collection_mode`，统计/对账必须按订单快照口径，不能按商家当前配置回推。
