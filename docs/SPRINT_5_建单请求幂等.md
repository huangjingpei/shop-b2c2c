# Sprint 5：建单请求幂等

日期：2026-11-03

## 交付状态

D14 标记为已修复。沿用完整UUID订单号，补齐请求幂等键、并发重放、失败回滚，以及唯一键碰撞时最多3次的整事务重试。该能力作用于建单，不是支付、退款或渠道通知幂等的替代品。

## HTTP契约

三个入口均必须携带`Idempotency-Key`：

| 入口 | 作用域 |
| --- | --- |
| POST /api/v1/public/orders/checkout | 匿名自购建单 |
| POST /api/v1/peer-pay/buyer/create | 匿名买家求助代付 |
| POST /api/v1/merchant/orders/push-pay | 当前会话店铺 + 操作人 |

键允许16–128位字母、数字、下划线及短横线。调用方须使用安全随机源生成至少128位随机性的键，不能使用订单参数、手机号或可预测流水。原始键不落库，存储作用域与键的SHA-256摘要；请求参数另存摘要。

- 同一作用域、同键、同参数：返回第一次成功建单的响应快照，不再生成订单、明细、海报或新查单凭证。
- 同一作用域、同键、不同参数：业务code为409，保留原订单；当前业务异常处理仍可能使用HTTP 200包装，客户端必须读取业务code。
- 缺少或非法键：业务code为400，不执行建单。缺少必需请求头时HTTP状态也是400；提供了头但格式非法时沿用现有业务异常响应契约。
- 不同键表示不同的购买意图，允许同款再次购买。不同接口、不同商户或操作人可使用相同原始键，记录互不串用。

参数摘要对JSON属性排序，但不会把不同金额精度、空字符串与null、不同联系人等自动视为相同。更新请求DTO的字段或默认值时需要评估旧摘要兼容和作用域版本，不能静默改契约后承诺任意旧请求仍可重放。

响应快照是“原始建单结果”，其中UNPAID等字段不是订单当前实时状态；付款、到期或履约进度必须再查询订单。即使当前商品已下架，重放也只返回旧结果，不创建新订单、不恢复已过期的付款资格。

## 事务与安全边界

`order_idempotency`以摘要作为主键。先通过不覆盖参数摘要的upsert获得同键数据库互斥，再锁行检查参数与响应。占位、订单、明细和响应快照全部在同一事务中提交；任何异常一起回滚，后续可携原键重新尝试。

唯一订单号/分享token等数据库唯一键碰撞时，必须先回滚整笔事务，再开启新事务重新执行；最多尝试3次。并非所有数据库故障都自动重试，超时/死锁等失败后调用方仍应复用原键。幂等服务禁止在已有业务事务中调用，避免在已失败的外层事务内进行伪重试；其业务回调必须加入该服务持有的事务。

匿名入口没有登录身份，持有强随机幂等键就能重放相应建单结果。该键应按私密重试凭证保管，不能放进公开分享链接、日志或统计埋点；分享仍使用专门的peerPayToken。商家作用域由会话身份构成，不信任请求中的商户字段。

响应快照可能含联系方式、queryToken、分享凭证及海报，数据库访问应受控。本轮不自动过期/清理幂等记录，避免清理后旧键重新建单；容量与保留策略仍需后续制定。记录清理不能独立于订单和凭证生命周期随意进行。

## 前端与部署兼容

商城自购、买家代付及商家推单分别维护提交上下文：相同参数的网络失败重试复用键，参数变化生成新键；只有收到业务成功才清理。发送时使用独立请求体快照，避免表单在异步发送前被编辑，导致请求体与幂等键不对应。不能在finally、网络错误或业务失败时清理键。

当前键只保存在页面内存。刷新、关闭页面或其他客户端需要继续同一请求时，调用方须自行保存并带回原键；系统不会仅凭“相同商品和联系方式”判断是不是重复购买。页面使用浏览器安全随机UUID，部署须提供支持`crypto.randomUUID`的浏览器和安全上下文。

这是HTTP契约变化：旧客户端不带键会被拒绝，需要同步发布三端并提示仍停留旧页面的用户刷新。新前端给旧后端发送额外请求头是兼容的，但旧后端不会提供幂等保护，不能在混合发布窗口宣称完整保证。后端内部checkout/建单服务保留为事务内业务方法，不应绕开HTTP门面另开未保护的公开接口。
