## 1. 审查结论与范围

当前项目属于“多商户商品展示 + 免登录单品购买 + 找人代付/商家推单”的演示型 MVP。三端页面和基础 CRUD 已存在，但真实支付、资金结算、并发库存、售后仲裁与财务对账尚不足以支撑真实电商经营。建议优先完成支付可信边界、多商户隔离和库存一致性整改，再扩展业务功能。

已扫描后端 Controller、Service、Mapper、Entity、DTO、配置和 SQL；管理端及商城端页面、路由与请求代码；启动、云部署、Nginx、备份脚本；README 与现有 Markdown 设计/交付文档。二进制设计文档不作为代码落地证据，依赖目录和构建产物不作为自研业务审查对象。未发现适用于当前目录的 AGENTS.md。

本报告为源码静态审查，没有启动服务、连接数据库、触发支付或执行部署，也没有进行并发压测和线上验证。“已确认缺陷”表示代码路径存在问题；实际触发概率和损失范围仍需测试。“未实现”表示当前仓库中未找到端到端实现，不能据此断言外部系统没有相应能力。没有开展依赖漏洞数据库扫描或法律合规审查。

优先级：P0 为真实交易上线前必须处理的资金、资产或租户隔离问题；P1 为核心经营闭环缺口；P2 为体验、治理与工程完善；P3 为业务扩展候选。功能缺口的优先级基于当前同时经营实物、卡密和线上服务的定位。

## 5. 与现有文档的主要差距

1. `B2B2C_MVP_PEER_PAY_DELIVERY_REPORT.md` 的“100%落地”“全闭环”“原子预占库存”不能作为当前生产验收依据：目前有订单级 Redis 锁，没有跨订单 SKU 预占，支付和分账仍是模拟。
2. “三方不可篡改对账台账”目前是可 updateById 的订单字段；缺少独立支付事件、不可覆盖审计记录和渠道对账。前端随机付款人 ID 也不能证明实际付款人身份。
3. 设计规范已列出投诉仲裁、日/月对账和广告管理，现有代码主要停留在数据表或读取能力；退款状态机也未形成闭环。
4. README 仍描述 JPA/repository、JWT 等结构，实际使用 MyBatis-Plus/Mapper 与 Sa-Token；SQL 权威路径实际为 `src/main/resources/db/schema.sql`。历史报告端口8082与当前默认8080也有差异。
5. 阿里云文档与脚本残留 PDK、Uni-app 和其他工程路径；应以实际可执行部署演练为准。腾讯云方案更接近当前工程，但同样需要数据库名、密钥、种子数据和恢复能力验证。
6. “防封”“担保交易”“微信直结生效”等界面和交付表述没有被当前渠道接入或技术实现充分支持，应与实际能力同步更新。本项是产品真实性核对，不构成法律结论。

## 6. 建议整改顺序与验收要点

### 第一批：真实交易上线门槛

- 处理 D01–D06、D15–D16，建立可信支付、SKU 归属校验、租户隔离、原子库存和发卡幂等。生产构建不能暴露 Mock 支付。
- 补齐 F01 及经营模式对应的支付确认；演示环境必须明确标记并隔离数据。处理敏感实体返回、密钥和种子账号问题。
- 验收：无有效到账结果不能发卡；两个商家相互不可读写资产；末份库存并发购买最多一笔成功；一张卡密只分配一次；同一支付通知并发/重放不重复扣减或发货。

### 第二批：核心经营闭环

- 落地真实预占与订单状态机、关闭/补偿任务；区分卡密与定制服务；补地址、收货、退款、投诉和仲裁。
- 完成渠道资金流水、商户账单与差异核对，明确服务费和抽佣的收费模型。
- 验收：取消/超时/失败均可追溯恢复；退款回到原付款人且账务一致；实物可从下单走到完成/售后；卡密缺货不能静默变成定制服务。

### 第三批：运营与工程治理

- 完成商品维护、员工权限、通知、审计、广告管理和准确经营指标；统一部署资产与版本迁移。
- 仓库已有 npm lockfile 和数据库备份脚本，应在其基础上补 CI、恢复演练、监控告警和可重复部署验证，不应将已有脚本误判为不存在。
- 验收：生产配置无固定密钥与默认演示账号；新装与存量升级均成功；备份实际可恢复；看板能区分未付款、已支付、退款和已结算。

### 第四批：确认范围后扩展

会员、购物车、营销、批发、多币种等按经营方向决策。优先修复现有单店单商品交易闭环，避免把扩展候选全部作为当前 MVP 必须实现的功能。
