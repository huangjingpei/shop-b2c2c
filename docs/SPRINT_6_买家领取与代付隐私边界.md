## 付款人与买家的能力分离

`peerPayToken`用于公开查看账单、分享和付款流程，不能用于提取交付内容。代付成功页仅提示付款结果和买家查单，不把公开链接视为领取授权。原公开Mock支付入口仍不存在，内部支付方法也未重新暴露。

`queryToken`为买家私密领取凭证。自购、买家代付及商家推单均生成完整UUID的32位十六进制值，并在创建响应中交给发起人；不写入微信分享文本、付款链接或海报参数。预占的`ownerToken`继续只授权取消预占，不能代替queryToken领取。

自购和买家代付页面明确展示订单号及领取凭证，用户关闭窗口前应私密保存。商家推单在后台单独显示凭证与查询联系标识，商家只能通过私密渠道交给买家，不能复制进付款分享卡片。历史推单允许不填写联系方式，届时响应会给出系统保存的联系标识，买家查询需要使用这个值。

付款人也可能就是买家，但只有实际持有独立领取凭证时才有领取能力；单凭“我付了款”、分享链接或知道手机号不构成提货授权。

## 查单接口

旧`GET /api/v1/public/orders/quick-search`已停用，固定返回HTTP 410及业务code 410，不读取或返回订单。新接口：

```text
POST /api/v1/public/orders/quick-search
Content-Type: application/json

{
  "orderSn": "订单号",
  "contact": "下单联系标识",
  "queryToken": "买家私密领取凭证"
}
```

三项都必填，单字段最多64字符，校验时去除首尾空格；订单号仅接受ASCII字母、数字、短横线和下划线；领取凭证大小写敏感，验证使用常量时间比较方法。订单不存在、联系方式错误和凭证错误均使用相同的业务code 400和消息，不告诉调用方哪一项命中。

成功结果保持order/items/store三部分以兼容页面，但不再直接序列化实体：

- order只含订单号、状态、类型、金额、创建时间及必要的交付/物流信息。
- items只含买家购买快照；仅类型2且COMPLETED可返回cardDetails。
- 仅类型3且COMPLETED可返回serviceVoucher；仅实物已发货或完成时返回物流字段。
- 不返回queryToken、peerPayToken、付款人ID、渠道流水、佣金/商家结算金额或内部订单关联字段；store沿用6字段公开白名单。

领取响应设Cache-Control: no-store。联系方式与凭证只放POST请求体；页面只把订单号放入查单链接，不从URL自动接收凭证。旧链接里的其他查询参数和fragment在页面初始化时清除，但无法撤回已经产生的旧浏览记录、访问日志或历史交付内容。

现有业务异常处理仍有HTTP 200包装业务错误的情况，客户端须校验业务code；前端已处理400/429/503等业务失败，不把空响应当成查询成功。

## 限流与运行条件

Redis单键Lua对INCR和EXPIRE原子执行，窗口为5分钟；订单号大小写变体共享计数，同一订单最多60次，同一连接IP最多300次。计数键仅保存摘要，不保存联系方式或领取凭证。Redis异常或返回空值时业务code为503，不回退到匿名查询；超额时为429。

当前只使用连接端IP，不直接相信客户端提交的X-Forwarded-For。Nginx等代理之后可能共享IP桶，部署时需要核对可信代理设置、正常请求量和限流策略；不能为避免共享桶而无条件信任外部代理头。Redis ACL需要允许相应键前缀及脚本执行/计数/过期命令。本轮使用Mock Redis验证决策，尚未做真实Redis Lua、ACL、多实例和代理联调，因此D20保留部分修复。

服务端不再把卡密SQL参数、服务交付凭证、买家联系方式及付款人标识直接写入相关业务日志。请求解析错误不记录或回显原JSON，通用错误响应不再附带内部异常文本；内部异常堆栈等其他日志边界仍需另行治理，不宣称已完成全部隐私审计。

## 升级与未完成事项

- 没有新增字段或表，query_token原有VARCHAR(64)足够；**不需要再删除或重建数据库**。
- 前后端需要同步发布。旧GET查单客户端须改为POST并取得领取凭证；旧页面缓存需要刷新。
- 旧订单已有的领取凭证仍按原值校验，本轮不自动轮换。旧幂等响应若没有领取凭证，不会因重试自动重写历史快照。
- 遗失凭证不能仅靠订单号/手机号绕过领取校验。自动短信/邮箱验证、账号绑定、安全找回及凭证重发/撤销未实现；需商家通过授权信息核实后处理，不能提供匿名回退接口。
- 当前仍无真实支付渠道；本轮是隐私与领取能力闭环，不代表已开放真实付款、退款或渠道补偿。
