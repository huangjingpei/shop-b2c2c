## 1. 必须开工前定（金额与订单模型）

### Q01 费率快照还是实时费率（原 S01 + 设计 §5.4 + 原 §5 B08）

**已确认（用户 2026-11-06）：A 订单级快照。** 之后调价不影响存量单；调价生效时点 S07 已确认 B（次日 00:00，降费可即时、调高必须次日），只影响新单。

**到底在决定什么**：商家以 5% 卖出 100 元，管理员随后把费率调到 8%。这单结算时按 5% 还是 8%？新费率从什么时候开始影响订单？

**选项**

- **A. 下单时快照（推荐）**：下单就把费率、计费基数、服务费额、政策版本写进订单；之后调价不影响这单。
  - 作用：金额可预期、可审计、对账可复现，退款能按原费率冲正。
  - 代价：调价只影响新单；若运营调错，只能冲正/补政策，不能改历史。
- **B. 结算时读实时费率**：结算任务按商家当前费率统一算所有未结算单。
  - 作用：调价立即覆盖未结算订单。
  - 代价：下单后金额会变，买家和商家无法预期；退款时费率先变，冲正金额无法复现；审计困难。
- **C. 支付成功时快照**：下单只展示预估，支付成功时按当时费率写死。
  - 作用：比实时结算稳定，又允许下单到支付之间调价。
  - 代价：下单页金额与最终扣费可能不一致，需要补差/提示；实现比 A 多一步。

**原推荐（已被用户确认）**：A（订单级快照）。理由：现有代码已在下单时算 `commission_amount`，顺现状收敛；阶段二分账也必须在支付成功时确定平台留成；退款冲正必须能复现原费率。
**已确认（用户 2026-11-06）**：选择 A；B 被否决（金额后变、退款不可复现、审计困难），C 未采用（下单展示与扣费金额可能不一致）。

**影响范围**：影响 T39（费率政策）、T32（支付事件读快照）、T34（账本/结算）；需新增订单费用快照列（`fee_rate_bps/fee_base_amount/fee_amount/fee_policy_id/fee_status`）；会改写设计 §5.4 与 §5.5，并影响修复清单 T34 的实现口径。

**阻塞**：**已确认**。

### Q02 服务费扣费时点（原 S01 + 原 §5 B08）

**已确认（用户 2026-11-06）：A 余额充足时支付成功即扣，平台不留敞口。** 补充：账期可配置 7/21/30 天，用于余额不足时的欠费宽限；高频商家账期更短，系统给建议值但需管理员确认；推广期可设 0 费率。

**到底在决定什么**：订单支付成功后，平台什么时候真正从商家的服务费余额里扣钱？

**选项**

- **A. 支付成功立即扣**：回调成功就记应收并扣余额。
  - 作用：平台回款最快，欠费窗口最小。
  - 代价：退款频繁时要反复冲正；余额不足会影响已成交订单，容易产生“订单成功但费用扣不动”。
- **B. 结算周期扣（推荐）**：支付成功只记“应收”，到结算日汇总扣款。
  - 作用：退款可在结算前直接抵扣，账务清晰；与结算单、对账天然一致。
  - 代价：平台要垫一个账期；必须维护应收/已收/已冲正状态。
- **C. 发货/完成时扣**：履约完成才计费。
  - 作用：与“实际交付”绑定，纠纷少。
  - 代价：虚拟商品/长期未发货订单会长期挂账；退款与履约状态组合更复杂。
- **D. 下单冻结、结算确认后扣**：下单先冻结预存余额，结算再实扣。
  - 作用：防欠费效果最好。
  - 代价：冻结账本、解冻、超时释放都要做，复杂度最高。

**原推荐（已被用户否决）**：B（结算周期扣，支付成功只记应收）。理由：阶段一不碰货款，服务费按账期结算最清晰；退款可在结算前抵扣，避免频繁冲正。**已确认 Q02-A**：余额充足时支付成功即扣，不按结算周期统一扣；B 不采用。
**已确认（用户 2026-11-06）**：选择 A，不采用 B/C/D。补充规则：余额不足时按 7/21/30 天账期欠费宽限；高频商家账期更短；系统建议值必须管理员确认；0% 推广照常生成计费记录并区分应收/免收。

**影响范围**：影响 T34（账户/账本/结算单）、T33（退款冲正）、T35（欠费对账）；需 `merchant_account/ledger`、订单 `fee_status`；会改写设计 §8.2 与 T34 卡。

**阻塞**：**已确认**。

### Q03 退款责任与服务费冲正（原 S03 + 原 §5 B08）

**已确认（用户 2026-11-06）：C 按收款模式分流。** 阶段一商家直收由商家退款、平台只冲正服务费；阶段二平台代收由平台退款；接口按 `collection_mode` 分叉。

**到底在决定什么**：买家退款时，谁去操作退款？平台已经记/收的服务费怎么退？部分退款怎么算？

**选项**

- **A. 商家自行退款，平台只冲正服务费（推荐）**：货款由商家原路退，平台按原快照冲正服务费。
  - 作用：阶段一平台不碰货款，合规边界清晰；平台责任最小。
  - 代价：平台无法直接控制退款时效，需商家回填退款凭证；恶意不退需人工介入。
- **B. 平台代退，再从商家余额/结算扣回**：平台统一操作退款。
  - 作用：买家体验统一，退款时效可控。
  - 代价：平台需要垫资或代收货款，阶段一接近“二清”，不建议；需额外追偿机制。
- **C. 按收款模式分流**：商家直收由商家退，平台代收由平台退。
  - 作用：适配阶段一/阶段二双模式。
  - 代价：退款入口、责任、对账都要按 `collection_mode` 分叉，复杂度上升。
- **D. 服务费不退**：退款只退货款，服务费照收。
  - 作用：实现最简单，平台收入稳定。
  - 代价：商家争议大，部分退款时明显不公平，存在合规/客诉风险。

**原推荐（已被用户否决）**：A。理由：阶段一平台不代收货款，由商家退款、平台只冲正服务费，既合规又不需要平台垫资。

### Q04 计费基数（原 S06 + 原 S10 + 原 §5 B08）

**已确认（用户 2026-11-06）：B 商品成交额。** 商品成交额 = 单价×数量－商家优惠；剔除运费、平台优惠/补贴、税费；必须新增字段，不用实付额过渡；平台补贴计平台成本，不向商家收服务费。

**选项**

- **A. 按订单 `pay_amount` 全额**：现在能付多少就按多少计费。
  - 作用：最简单，与现状代码等价。
  - 代价：运费、平台优惠都进了基数，商家为不是自己收入的部分付服务费。
- **B. 商品成交额（单价×数量－商家优惠），不含运费、平台优惠、税费（推荐）**：只对商家商品收入计费。

- **C. 商品成交额 + 运费**：运费也计服务费。

  - 代价：运费争议大，商家可能把运费拆低或线下另收。
- **D. 按渠道实收扣除平台补贴**：以实际到账金额为基数。

### Q05 费率含税与发票（原 S02 + 原 S12 + 原 §5 B08）

- **B. 含税价，费率即全部，平台开票**：8% 就是商家最终成本，税额内含。

### Q06 服务费结算周期（原 S05 + 原 §5 B08）

**已确认（用户 2026-11-06）：C 月结。** 后台必须同时提供**逐笔明细查询**；结算单是汇总，明细是证据。日结（A）不采用（账单/对账频率过高）；周结（B）不采用（用户明确选月结，不得按“默认周结”实现）；按订单实时结算（D）与已确认的 Q02-A 扣费时点语义不同，仅预存余额场景可用，不作为结算周期。

**到底在决定什么**：服务费多久结一次账、生成一张结算单？

**选项**

- **A. 日结**：每天生成结算单并扣费。
  - 作用：回款快，欠费窗口小，商家每天能看到账。
  - 代价：账单/对账频率高，运营和渠道流水匹配成本大。
- **B. 周结（推荐）**：每周固定一天结算上一周期。

- **C. 月结**：每月结算一次。
  - 作用：运营最简单，账单少。
  - 代价：欠费风险最大，商家对账滞后，退款跨期调整多。
- **D. 按订单实时结算（仅预存余额）**：每单支付成功即扣。
  - 作用：无账期、无欠费。
  - 代价：退款冲正频繁，账单碎片化，和 Q02 的 B 方案冲突。

**原推荐（已被用户否决）**：B（周结）。理由：阶段一商家数量有限，周结足以控制欠费，又不会像日结那样产生大量账单；可按商户等级后续调整。
**已确认（用户 2026-11-06）**：选择 C 月结；同时**必须提供逐笔明细查询**，明细可按下单/支付时间、订单号、退款单号、费用状态筛选，并能追到 `payment_event_id/refund_id` 与订单快照费率。B 周结不采用。

**影响范围**：影响 T34（结算批次/明细）、T35（对账/差异）；需 `merchant_settlement_batch` 的 `period_start/period_end` 与唯一约束；会改写设计 §9.3 与 T34/T35 卡。
